# Замер моделей

Папка с задачами, у которых известен правильный ответ, и скрипт, который гоняет по ним
любую модель. Нужна, чтобы вопрос «стоит ли добавлять модель X» решался прогоном,
а не спором.

## Прогнать

```bash
./run.sh openrouter/moonshotai/kimi-k2.7-code
```

Один случай, если нужно быстро:

```bash
./run.sh deepseek/deepseek-chat 01-tokens
```

`run.sh` (и `bench.sh run`) на каждый вызов по-настоящему обращается к модели и тратит
вызов подписки или ключа провайдера; сухого режима нет. Проверить сам метод без сети
можно только через `selftest.sh` и `rescore.sh`.

Вывод — таблица «найдено из ожидаемого», число ложных срабатываний и время.
Каждый прогон дописывает строки в `results/log.csv`, ответы моделей целиком
складываются в `results/<дата>_<модель>/`.

**Столбец ложных срабатываний починен 30.08.2026.** До этого счётчик считал
обвинением любое упоминание символа: фраза «в `bump_counter` ошибки нет»
записывалась модели в выдумки, то есть аккуратность наказывалась. Теперь
упоминание засчитывается только на строках без маркера снятия обвинения,
а локаль задаётся внутри скрипта — без UTF-8 `grep -i` не знает кириллического
регистра, и маркер терялся молча. Числа в этом столбце по прогонам старше
30.08.2026 сравнивать между моделями нельзя.

## Как читать

**Найдено** — сколько заложенных ошибок модель назвала. Главное число.

**Ложных** — сколько раз она обругала заведомо исправный код. Модель, которая
объявляет багом всё подряд, наберёт полный счёт по первой колонке и провалится по второй.

**Случай `05-volume`** стоит особняком. В нём те же классы ошибок, что в 01-04,
но файл на сотню строк. Если модель находит ошибку в коротком файле и теряет
такую же в длинном — дело в объёме, а не в модели, и лечится это нарезкой,
а не переходом на модель подороже.

## Как считается
Каждый случай — папка с исходником, файлом `expect.txt` и, если есть заведомо
исправный код, файлом `forbid.txt`. Строка в этих файлах — регулярное выражение,
которое ищется в ответе модели без учёта регистра.

Шаблон должен ловить находку в **любой** формулировке, потому что модели описывают
ошибку по-разному: одна назовёт функцию, другая укажет только номер строки. Поэтому
в шаблон через `|` идут все опознавательные признаки сразу:

```
issue_stamp|created_at or time|tokens.py:7
```

Это не педантизм. На первом же прогоне DeepSeek нашла ошибку с `or`, но написала
только `tokens.py:7`, и шаблон из одного имени функции засчитал промах вместо находки.
Замер, который врёт в эту сторону, хуже отсутствия замера.

Оценка не использует ещё одну модель намеренно: судья-модель добавляет свои ошибки
и свою цену, а признак в тексте либо есть, либо нет.

## Добавить случай

```
cases/06-моё/
  что_нибудь.py    исходник
  expect.txt       по строке на каждую заложенную ошибку
  forbid.txt       по строке на каждый исправный кусок (необязательно)
  notes.md         что именно заложено и почему это ошибка
```

Два требования к заложенной ошибке:

1. **Бесспорность.** Если она обсуждаема — это не задача для замера. Нужен внятный
   сценарий отказа: такие-то входные данные дадут такой-то неверный результат.
2. **Опознаваемость.** Ошибка живёт в функции, чьё имя больше нигде в файле не
   встречается, и шаблон в `expect.txt` перечисляет через `|` имя, характерный кусок
   кода и номер строки. Иначе засчитаешь промах там, где модель была права.

В `notes.md` описывать не только ошибки, но и чистые куски — через полгода
будет непонятно, почему `bump_counter` в `forbid.txt`.

## Проверить сам счётчик

```bash
./selftest.sh
```

Моделей не трогает, работает мгновенно. Гонять после любой правки `score.sh`.

## После правки счётчика

`score.sh` меняли — обязательно прогнать оба:

```bash
./selftest.sh    # проверяет счётчик на заготовленных ответах
./rescore.sh     # пересобирает results/log.csv из сохранённых ответов моделей
```

Без второго в журнале остаются цифры, посчитанные старой версией, и тренд врёт.

Счётчик нормализует ответ перед сравнением, приводя все способы записи ссылки на строку к виду `файл.py:число`. Формы, которые уже встречались в живых ответах и заведены в `selftest.sh`:

```
tokens.py:7
**tokens.py, строки 7-9**
в файле `tokens.py` на строке 7
tokens.py line 7
```

Встретишь новую — добавь проверку в `selftest.sh` прежде, чем править регулярное выражение.

Кириллицу нельзя класть внутрь `[ ]` в `sed`: вне UTF-8 локали класс распадается на байты и молча перестаёт срабатывать. Только полнословные альтернативы через `|`.

## Сорванный прогон

`score.sh` возвращает код 2 и печатает `- - -`, если в ответе видны признаки отказа: HTTP 500, лимит запросов, таймаут. В таблице такой прогон помечается `сорвано` и в сумму не идёт.

Это не мелочь. `gemini-3.1-pro-preview` уронил шесть прогонов из девяти, и без этой проверки его отказы читались как «модель ничего не нашла».

## Модель не должна видеть ответы

Самая дорогая ошибка этого стенда, найденная 2026-08-24 и стоившая полного перезапуска.

Агент OpenCode не читает только тот файл, который назвали в задании. Он делает `Glob **/*` по рабочему каталогу и читает всё, что найдёт. А в каталоге случая рядом с исходником лежали `expect.txt`, `forbid.txt` и `notes.md` — то есть ответы.

Kimi на случае `05-volume` прочитала `notes.md`, `expect.txt` и `forbid.txt`, после чего «нашла» ровно три заложенные ошибки с формулировками из `notes.md`. Проверка по всем сохранённым ответам: **11 прогонов из 44** читали ключ.

Поэтому `run.sh` теперь копирует **один** исходник во временный каталог и запускает модель там:

```bash
WORK=$(mktemp -d)
cp "$SRC" "$WORK/"
( cd "$WORK" && opencode run ... )
rm -rf "$WORK"
```

Проверять это при каждой правке `run.sh`:

```bash
grep -cE 'Read (notes|expect|forbid)' results/*/*.txt
```

Ноль — чисто. Больше нуля — все цифры этого прогона недействительны, каталог в архив и перезапуск.

Общее правило, которое отсюда следует: **всё, что знает ответ, должно лежать вне досягаемости модели**. Не «в другом файле», а вне рабочего каталога. Агент с доступом к файловой системе найдёт подсказку, если она достижима, и результат будет выглядеть как отличная работа модели.

## Один прогон ничего не измеряет

Разброс между прогонами одной и той же модели на одном и том же случае оказался больше, чем разница между разными моделями.

Примеры из журнала: `kimi` на `02-orders` — 2 из 3, затем 0 из 3. `deepseek` на `05-volume` — 2 из 3, затем 3 из 3.

Отсюда: **прежде чем делать вывод о модели, прогнать её три раза** и смотреть на разброс, а не на одно число. Разница меньше трёх пунктов из четырнадцати — шум.

Три прогона пяти моделей стоят около двух долларов и занимают минут двадцать. Это дешевле, чем полгода раздавать роли по случайному числу.

## Сводка по нескольким прогонам

```bash
./summary.sh
```

Печатает по каждой модели: сколько было **полных** прогонов, лучший и худший результат, ложные срабатывания и время. Ниже — список случаев, где прогоны одной и той же модели разошлись между собой.

Второй список важнее первого. Если модель на одном случае даёт то 0, то 3, её среднее ничего не значит, и сравнивать её с другой моделью по одному числу нельзя.

Незавершённые прогоны в счёт не идут: идущий прямо сейчас прогон иначе выглядит как провал модели.
